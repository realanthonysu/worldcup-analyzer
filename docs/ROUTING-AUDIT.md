### 二、发现的问题

按严重程度分级：P0 = 逻辑缺陷（会导致错误路由），P1 = 设计模糊（可能导致错误行为），P2 = 覆盖缺口（缺少测试或处理），P3 = 文档瑕疵。

---

#### P0-1: 赛事结束后，未参赛球队也会进入"世界杯复盘"

**位置**：SKILL.md Phase 1 表，"赛事已结束"行

**问题**：Phase 1 "赛事已结束"行写道"无论输入球队、球员还是教练，直接分析其在 2026 美加墨世界杯的旅程"，并跳过搜索验证。但如果用户输入一支**未参加**本届世界杯的球队（如 `/worldcup-analyzer 中国`，日期设为 07-21），系统会尝试输出"世界杯复盘"，但该队根本没有本届世界杯的旅程、表现或高光时刻可分析。

**当前路由**：`中国` → Phase 0（有效球队） → Phase 1（赛事已结束） → 跳过搜索 → 世界杯复盘变体 → 模板无法产出有意义内容

**正确路由**：应该先验证该队是否参赛，未参赛则路由到历史模式。

**修复建议**：在"赛事已结束"行增加轻量级参赛验证——搜索确认该队参赛后进入世界杯复盘，确认未参赛则进入历史模式。这与"赛事未开始"阶段的参赛验证逻辑对称。

**影响范围**：SKILL.md Phase 1 表 + post-match.md 世界杯复盘变体（增加前置条件说明） + 可能需要新增测试场景。

---

#### P0-2: 教练输入 + 赛事进行中 + 球队被淘汰 → 路由到错误模板

**位置**：SKILL.md 路由表 v2，Step 3a

**问题**：路由表 v2 不区分输入类型（球队 vs 教练）。Step 3a "全部踢完 + 确认淘汰" 路由到 `[post-match.md] §赛事复盘变体`，这是球队视角的模板。当用户输入教练名（如 `/worldcup-analyzer 德尚`，法国小组赛出局），系统会用球队模板输出复盘，而非教练视角的 `coach.md §世界杯复盘变体`。

**当前路由**：`德尚` → Phase 0（教练） → Phase 1（进行中） → 搜索验证 → Step 3a → **post-match.md §赛事复盘变体**（错误：球队视角）

**正确路由**：教练输入 + 球队被淘汰 → `coach.md §世界杯复盘变体`（教练视角的执教复盘）

**修复建议**：在路由表 v2 中为 Step 3a 增加输入类型分支——球队输入走 post-match.md，教练输入走 coach.md。或者在路由表下方增加注释："教练输入在 Step 3a 走 coach.md §世界杯复盘变体，不走 post-match.md"。

**影响范围**：SKILL.md 路由表 v2 + Quick Reference [C] 行。

---

#### P0-3: 赛事结束后 + 教练已离任 → 被拒收，无法进入世界杯复盘

**位置**：SKILL.md Phase 1 "赛事已结束"行 + 教练验证 Priority 1

**问题**：Phase 1 的注释说"教练输入跳过教练验证中的'是否参赛'检查"，但未说跳过 Priority 1（不再执教/退休）。世界杯结束后教练离任是极为常见的场景（如 2022 世界杯后多位教练辞职），此时球迷想回顾该教练的世界杯执教旅程，但会被 P1 拒收。

**当前路由**：`德尚`（07-21，德尚已于 07-20 宣布离任） → Phase 0（教练） → Phase 1（赛事已结束） → 教练验证 P1（不再执教） → **拒收**（错误）

**正确路由**：赛事已结束 + 教练曾执教参赛队 → coach.md §世界杯复盘变体

**修复建议**：明确"赛事已结束"阶段跳过**全部教练验证**（不仅跳过"是否参赛"检查），直接以"该教练是否在本届世界杯执教过参赛队"作为唯一判定条件。或者修改 P1 文案，增加"赛事已结束"分支："该教练已不再执教。但因赛事已结束，仍可查看其世界杯执教复盘。"

**影响范围**：SKILL.md 教练验证 + Phase 1 注释。

---

#### P1-1: 球员输入 + 赛事进行中 + 球队未参赛 → 可能误入历史模式

**位置**：SKILL.md "前置：搜索验证" + 球员参赛验证的执行顺序

**问题**：赛事进行中，球员输入的执行顺序是：Phase 0（识别为球员）→ Phase 1 搜索验证（查球队赛程）→ 路由表 → 球员参赛验证。如果球员所属国家队未参赛（如莱万多夫斯基，波兰未参赛），搜索验证会找不到赛程 → 路由到历史模式。但正确的处理应该是球员验证 P2 拒收（"{球员名} 所属的 {国家队名} 未参加 2026 世界杯"）。

**当前路由**：`莱万多夫斯基` → Phase 0（球员） → Phase 1 搜索验证（查波兰赛程 → 无赛程） → **历史模式**（不够精确）

**理想路由**：`莱万多夫斯基` → Phase 0（球员） → 球员参赛验证 P2（波兰未参赛） → 拒收提示

**实际影响**：中等。历史模式也能提供有用信息（波兰的世界杯历史），但对球员输入的响应不够精准——用户期望的是"该球员无缘本届世界杯"的明确提示，而非球队历史回顾。

**修复建议**：在"前置：搜索验证"中增加球员模式分支——球员输入先执行球员参赛验证（确认国家队参赛），再执行搜索验证。或者在搜索验证的"无赛程"分支中，对球员输入增加二次判定。

---

#### P1-2: Phase 0 球员/教练双重身份的处理未明确

**位置**：SKILL.md Phase 0 判定表

**问题**：判定表将"足球教练"和"已退役球员"作为独立行，但未说明当输入同时匹配两者时如何处理。典型场景：齐达内（退役球员 + 知名教练）、德尚（前法国队球员 + 现法国队教练）、安切洛蒂（退役球员 + 俱乐部教练）。

当前 Phase 0 表的排列顺序暗示"教练"行在"退役球员"行之前（line 79 vs line 80），但不确定这是否是优先顺序。对于齐达内：如果先匹配"教练"行 → 进入教练验证 → P5（未执教）或 P4（纯俱乐部）→ 拒收；如果先匹配"退役球员" → 直接拒收。两种路径结果不同。

**修复建议**：在 Phase 0 注释中增加双重身份处理规则："当输入同时匹配'教练'和'退役球员'时，优先判定当前活跃身份。当前执教 → 教练模式；当前未执教 → 退役球员拒收。"

#### P1-3: Quick Reference [C] 的核心输出缺少"核心球员表现"

**位置**：SKILL.md Quick Reference 表，[C] 行

**问题**：[C] 行"五件套/核心输出"列为"战绩 / 关键比赛 / 出局归因 / 总结"（4 项），但实际模板 `post-match.md §赛事复盘变体` 有 5 节：一（完整战绩）、二（关键比赛）、三（核心球员表现）、四（出局归因）、五（总结）。"核心球员表现"被遗漏了。

**修复**：[C] 行改为"战绩 / 关键比赛 / 核心球员 / 出局归因 / 总结"。

---

#### P1-4: 路由表 v2 中 [B] 模式缺少淘汰赛阶段的测试覆盖

**位置**：路由表 Step 2c + 测试场景

**问题**：Step 2b（小组赛）和 Step 2c（淘汰赛）都路由到 [B] 复合模式，但区别在于下半段前瞻使用的模板不同（§小组赛 vs §淘汰赛）。S23 只测试了小组赛的 [B]，没有测试淘汰赛阶段的 [B]（如球队小组出线后踢了一场淘汰赛，还有下一场淘汰赛）。

**修复建议**：新增测试场景 S23b，覆盖淘汰赛阶段的 [B] 复合模式。

### 三、覆盖缺口（P2）

以下场景在路由逻辑中有定义但缺少对应测试场景，或路由逻辑本身未覆盖：

#### P2-1: 赛事进行中 + 未参赛球队 → 历史模式（无测试）

路由表"球队未参赛"行定义了此路径，但没有测试场景。如 `/worldcup-analyzer 中国` 在 06-15（赛事已开始）。

#### P2-2: 赛事进行中 + 教练（球队仍在比赛）→ 教练模式（无测试）

S15 的测试日期设为 06-06（赛事未开始）。缺少赛事进行中的教练模式测试（如 `/worldcup-analyzer 德尚` 在 06-15，法国有比赛待踢）。

#### P2-3: 赛事已结束 + 未参赛球队（无测试，且路由可能错误）

这是 P0-1 的测试缺口版本。`/worldcup-analyzer 中国` 在 07-21 应路由到哪里？当前设计会进入世界杯复盘，但正确路由是历史模式。

#### P2-4: 空输入 / 仅斜杠命令（无处理、无测试）

`/worldcup-analyzer`（无参数）的行为未定义。`argument-hint` 字段存在但 skill 内无空输入处理逻辑。模型可能会尝试分析"空字符串"，或输出使用提示。

**建议**：在 Phase 0 前增加空输入检查："若 `$0` 为空，输出使用提示：`请输入球队名、球员名或教练名。例如：/worldcup-analyzer 法国`"。

#### P2-5: 赛事已结束 + 教练已离任（无测试）

这是 P0-3 的测试缺口版本。如 `/worldcup-analyzer 德尚` 在 07-21，德尚已于 07-20 离任。

#### P2-6: [D] 淘汰赛赛前模式（无独立测试）

S25 覆盖了 [E] 出线等待，但没有覆盖 [D]（对手已定的淘汰赛赛前）。如球队已出线且下一轮对手已确定。

### 七、总体评价

路由系统的 Happy Path 设计非常扎实——v2 的"先回顾、再前瞻"逻辑清晰，6 种赛中模式 [A]-[F] 覆盖了从首战到收官的完整赛事进程。拒收体系（Phase 0 + 球员验证 + 教练验证）层次分明，文案差异化处理到位。

主要风险集中在**跨模式的交叉路径**上：当输入类型（教练/球员）与赛事状态（淘汰/结束）组合时，路由表 v2 默认按球队输入处理，缺少对教练输入的类型分支。三个 P0 问题中有两个源于此。修复方向是在路由表中增加输入类型感知，或在教练验证中增加赛中/赛后的特殊分支。

非预期输入方面，Phase 0 的防护门控覆盖了最常见的误用场景（俱乐部、非足球实体、退役球员等），对"明显非足球词汇免搜索"的优化也减少了不必要的搜索开销。球队昵称/球员昵称的识别依赖搜索引擎的智能匹配，通常可以工作但无显式保障。多实体输入和其他赛事名称是潜在的新球迷误用场景，当前未覆盖但风险较低。
